# 开发路线与进度

> 更新时间：2026-09-25 · 交付截止：2026-09-28

## 时间约束下的取舍

整个项目只有 3 天工期，所以从一开始就定了一条原则：
**每个阶段结束时都必须是可运行、可演示的状态**，绝不出现「做到一半跑不起来」。

因此顺序是「先打通闭环，再加深亮点」，并且对次要功能做了明确降级：

| 决定                 | 原因                                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------------------- |
| epub 解析降到最后    | 解析库选型与目录结构处理容易翻车，而 txt/md 已能验证「导入资料 → 生成路径」这条链路                           |
| 不引图表库           | 掌握状态用 CSS 画热力格即可，引一个图表库要多几百 KB 换一个视觉效果，不划算                                   |
| 单测只覆盖纯逻辑     | 排期算法与记忆检索的 bug 最隐蔽、最难靠手测发现；UI 的问题手测成本更低                                        |
| 不引 Markdown 解析库 | 模型回复里高频出现的只有代码块、行内代码、加粗、列表，自己写 120 行足够，还能避免流式输出时半截语法的渲染闪烁 |

### P4 · 记忆系统四层 ✅

## 验证记录

在 2026-09-25 完成的一轮验证中，**集成测试抓到了一个真实缺陷**并已修复：

> 掌握状态推导只读 `PlanItem.status`（排期项状态），而用户是在「今日」页勾选**待办**的 ——
> 两边判定口径不一致，导致「任务勾完了，掌握状态却不动」。
> 修复方式是把完成判定统一到 `planItemState(item, todos)`，并让 `syncMasteryFromPlan`
> 默认现读待办；同时在今日页勾选后真正调用回流（此前该函数**只在测试里被调用过**，
> 主循环的最后一环其实是断的）。

这类问题靠手测几乎发现不了 —— 它不报错、不白屏，只是那个最核心的卖点静默失效。

## 已知的未完成项

按重要性排序：

1. **资料文件导入（txt / md / epub）** —— 目前只能手动填写或让 AI 口述生成。
   这是原本规划的「第二条导入路径」，因为 3 天工期被降级到最后，最终没有做。
2. **计划自适应** —— 完成待办已经能回流更新知识点掌握状态，但还**不会自动重排**剩余计划。
   这是最值得做的下一步：当进度落后时，按剩余时间和剩余单元重新排期。
3. **学习统计** —— 没有学习时长趋势图，掌握状态只有当下的快照，看不到变化曲线。
4. **对话历史搜索** —— 会话多了之后只能靠标题辨认。
5. **完成情况回流只有单向** —— 目前是「勾选 → 掌握状态」；反向（掌握状态影响后续排期）还没做。

## 后续可以做的方向

- **计划自适应**：进度落后时自动重排剩余单元，这是闭环真正合上的最后一步
- 用向量检索替换关键词检索（记忆超过几千条后）
- 角色卡导入导出，便于分享
- 资料文件导入：txt / md 优先，epub 次之
- 本地通知之外，考虑浏览器推送（需要服务端）
