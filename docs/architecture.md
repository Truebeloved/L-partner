# 架构说明

本文说明 L-partner 的模块划分、数据流转，以及几个关键取舍背后的理由。

---

## 一、整体形态

**纯前端单页应用，无服务端。** 所有数据存在浏览器 IndexedDB 里，AI 能力由用户自填的
大模型 API 提供，请求从浏览器直接发往厂商。

这个选择是有代价的（用户必须自备 Key、网页关闭后无法主动提醒），换来的是：
打开即用、零部署成本、数据完全留在本地。对一个要被评委直接打开查看的作品来说，
这个交换是值得的 —— 详见 `design-decisions.md` 的 D1 与 D2。

```
┌─────────────────────────────────────────────────────┐
│  浏览器                                              │
│                                                     │
│  React 视图层（features/*）                          │
│        │                                            │
│        ├── zustand store ──► IndexedDB（持久化）      │
│        │                                            │
│        └── lib/llm 适配层 ──► 用户自填的模型 API      │
│                              （DeepSeek / Kimi / …） │
└─────────────────────────────────────────────────────┘
```

---

## 二、目录职责

```
src/
├── types/models.ts      全部数据模型，单一事实来源
├── store/               状态与持久化（每域一个 store，各自独立持久化）
│   ├── courses.ts       课程
│   ├── plans.ts         排期结果（以 courseId 为键）
│   ├── todos.ts         待办
│   ├── memory.ts        四层记忆
│   ├── personas.ts      角色卡
│   ├── chat.ts          对话
│   └── settings.ts      API 配置与偏好
├── lib/
│   ├── llm/             模型适配层：协议实现、错误翻译、提示词
│   ├── storage/         IndexedDB 持久化后端
│   ├── seed/            内置角色模板、示例课程
│   ├── date.ts          日期工具（统一用 YYYY-MM-DD 作为日期键）
│   └── id.ts            ID 生成
├── features/            按功能域组织，每个目录自带页面、组件与纯逻辑
│   ├── course/          课程创建与导入
│   ├── plan/            排期算法（纯函数）
│   ├── today/           今日待办
│   ├── reminder/        提醒调度
│   ├── chat/            对话
│   ├── persona/         角色管理
│   ├── memory/          记忆四层：检索、抽取、掌握状态
│   └── settings/        设置
└── components/          跨域复用的通用组件
```

**为什么按功能域而不是按技术分层**（不放 `components/ hooks/ utils/` 三大件）：
一个功能的页面、逻辑、测试放在一起，改动时不用在四个目录之间跳。
`features/memory/` 里同时有 UI、纯函数和测试，读这一块就能完整理解记忆系统。

## 三、数据模型要点

完整定义见 `src/types/models.ts`，这里只说三个关键设计。

### 1. 内容与排期分离

`Course`（含 `Stage` / `Unit`）描述**要学什么**，`PlanItem` 描述**哪天学**。

两者分离是为了让「重新排期」不破坏课程内容 —— 用户改了每周可投入时间，
只需要重新生成 `PlanItem`，章节结构原封不动。这也是「计划自适应」的前提。

### 2. 日期用 `YYYY-MM-DD` 字符串

不存时间戳也不用 UTC。学习计划是**按天**的概念，用带时区的时间戳会让
「今天」在不同时区下漂移。`DateKey` 类型在编译期就把这个约定钉住。

### 3. `Todo.planItemId` 是回流的关键

由计划生成的待办带着 `planItemId`，用户勾选完成时，系统能反推出
「哪个单元的哪个任务完成了」，进而更新知识点掌握状态。
用户手写的待办没有这个字段，因此不会错误地影响掌握状态。

## 四、三条关键链路

### 链路 1：主循环（无 AI 也能完整跑通）

```
用户创建课程 ──► buildSchedule() 纯函数排期 ──► Plan 落库
                                                  │
                                                  ▼
                              materializeTodos() 生成每日待办
                                                  │
                                                  ▼
                        今日页勾选完成 ──► syncMasteryFromPlan() 更新掌握状态
```

**`buildSchedule` 是纯函数**，不碰 store 也不碰 DOM。好处有两个：
可以用单测把边界情况钉死（现有 13 个用例）；以及它同时服务两条线路 ——
没有 API Key 时它就是最终排期器，有 Key 时它是 AI 方案的兜底与校验基准。

排期的规则优先级：

1. **deadline 优先** —— 按每周预算排不完时提高每日投入
2. **单日上限是硬约束** —— 宁可晚于 deadline 并如实告知，也不排出「一天学 5 小时」这种不可能执行的计划
3. **单元优先保持完整** —— 只有单个单元就超过单日预算时才跨天拆分

### 链路 2：对话上下文组装

每次发消息时，`buildSystemPrompt()` 把四段信息拼成 system prompt：

| 段   | 内容                                       | 作用                     |
| ---- | ------------------------------------------ | ------------------------ |
| 角色 | 身份、性格、说话风格、教学方式、禁忌       | 决定「它是谁、怎么说话」 |
| 情境 | 绑定的课程、目标、deadline、进度、今日待办 | 决定「它在帮你学什么」   |
| 记忆 | 检索出的相关记忆，按事实 / 掌握 / 情景分组 | 决定「它认识你多久了」   |
| 准则 | 不确定就说不确定、回答长度跟着问题走等     | 约束行为边界             |

记忆检索（`retrieveMemories`）是一个可解释的加权打分：置信度 × 层级权重，
叠加课程归属、关键词重叠（中文按二元组切）、新鲜度衰减、使用频次。

**没有引入向量库**：记忆条数通常在几百量级，关键词 + 结构信号已经够用，
而且打分过程完全可解释 —— 用户在记忆面板里能看懂「它为什么记得这个」。
引入 embedding 反而会让「为什么记得」变成第二个黑盒。

### 链路 3：记忆的写入与读取

```
对话进行中 ──每 8 条消息──► extractMemories() ──► 结构化 JSON ──► 去重 ──► 落库
                                                                    │
            下次对话 ──► retrieveMemories() ──► 注入 prompt ──► touch() 记录使用
```

**写入必须节流**：每轮对话都抽一次记忆会让 token 消耗失控。
策略是三条并行通道：

- **批量触发**：每积累 8 条消息抽一次
- **手动触发**：对话页的「记住这个」按钮
- **规则推导**：任务完成情况直接推导，**不消耗任何 LLM 调用**

**关于掌握状态的诚实边界**：规则推导只能把知识点标成「学习中」，永远不会标成
「已掌握」—— 完成待办只证明学过，不证明学会。`mastered` / `weak` 必须来自
LLM 从对话中的判断，或用户自己的修正。否则这个功能就退化成自欺欺人的进度条。

## 五、错误处理

`lib/llm` 把 HTTP 状态码和网络异常翻译成**可行动**的中文提示，而不是把原始报错抛给用户：

| 情况              | 提示重点                                         |
| ----------------- | ------------------------------------------------ |
| 网络不可达 / CORS | 区分两种可能，并说明 OpenAI 官方不允许浏览器直连 |
| 401 / 403         | 检查 Key 是否有效、是否有该模型权限              |
| 404               | 多半是 API 地址没有以 `/v1` 结尾                 |
| 429               | 限流或余额不足                                   |
| 5xx               | 服务端问题，建议换模型重试                       |

记忆抽取、会话摘要这类**后台增强**任务失败时静默跳过并打日志，
不会让用户觉得「刚才那次对话出错了」—— 它们失败不该影响主流程。

## 六、已知限制（有意为之，非缺陷）

1. **网页关闭后无法提醒。** 浏览器沙箱限制。页面内弹窗是主路径，系统通知是补充。
2. **数据不跨设备。** 没有服务端，所以没有同步。设置页提供 JSON 导出备份。
3. **API Key 存在 IndexedDB 里。** 这是纯前端方案的固有属性，UI 中已明确提示。
4. **不适合超大规模记忆。** 关键词检索在几千条量级会开始退化，届时需要引入向量检索。
5. **`epub` 解析未实现。** 当前资料导入支持 txt / md。

## 七、测试策略

只给**纯逻辑与关键链路**写测试，不追求覆盖率数字。共 102 个用例：

| 测试                                    | 覆盖内容                                                             | 用例数 |
| --------------------------------------- | -------------------------------------------------------------------- | ------ |
| `features/plan/schedule.test.ts`        | 排期边界：跨天拆分、非学习日、排不下时如实标记、单元完整性           | 13     |
| `features/memory/retrieve.test.ts`      | 检索排序：层级权重、课程归属、关键词命中、新鲜度、归档与低置信度过滤 | 11     |
| `features/memory/mastery.test.ts`       | 掌握状态推导与合并：规则只到「学习中」、不降级已有结论               | 11     |
| `features/reminder/reminder.test.ts`    | 提醒时刻计算：目标已过顺延、恰好等于当前时刻、跨天跨月               | 22     |
| `features/course/courseActions.test.ts` | 计划生成、待办物化的幂等性、重排、删除清理                           | 27     |
| `test/mainLoop.test.ts`                 | **主循环集成**：课程 → 计划 → 待办 → 掌握状态，含孤儿待办与历史保留  | 7      |
| `test/routes.smoke.test.tsx`            | 每个路由都能渲染而不崩                                               | 8      |
| `features/today/TodayPage.test.tsx`     | 今日页主路径：添加、勾选、进度、逾期分区                             | 3      |

为什么这么选：

- **排期与记忆检索的 bug 最隐蔽** —— 排期错了用户只会觉得「计划怪怪的」，很难描述清楚；
  记忆检索错了则是「它怎么不记得了」。这类问题靠手测基本发现不了。
- **主循环集成测试的价值最高** —— 它覆盖的正是**没有 API Key 时评审唯一能体验的路径**，
  而且 store 之间的协作（谁创建待办、重排会不会留孤儿、勾选有没有回流成掌握状态）
  最容易在重构中被悄悄改坏。事实上这条测试第一次运行就抓到了一个真实缺陷：
  掌握状态推导只看 `PlanItem.status`，而用户是在「今日」页勾待办的，
  两边判定口径不一致，导致「任务勾完了，掌握状态却不动」。
- **路由冒烟测试兜住白屏** —— 「能编译但一渲染就崩」这类问题类型检查抓不到，
  但会让整页白屏，对要交给别人打开的项目来说代价最高。
