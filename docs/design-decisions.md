## D1. AI 能力如何接入？（最关键的架构岔路）

**背景**：内置互动 AI 需要一个 LLM。若前端直连厂商接口，API Key 会暴露在浏览器里。

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| A. 纯前端 + 用户自填 Key（存 localStorage） | 零后端、零部署成本，评委可直接打开链接体验 | 用户需自备 Key；Key 存在浏览器本地 |
| B. 纯前端 + 内置离线 Demo 模式（预置题库/模拟回答），真实 Key 可选 | **打开即用、断网可演示**，面试场景最稳；同时保留真实 AI 能力 | 需要额外写一层 Mock 适配 |
| C. 纯前端 + 轻量后端代理（Workers / Node） | Key 不落地浏览器，更像真实产品架构 | 部署链路变长，演示门槛提高 |

**结论**：待定（倾向 A + B 组合）

## D2. 提醒（学习弹窗）的实现形态

**背景**：纯 Web 前端的提醒能力有物理上限 —— 页面关闭后无法主动唤起系统通知（除非引入 Service Worker 推送，仍需服务端）。

| 方案 | 能力 | 限制 |
| --- | --- | --- |
| A. 页面内弹窗 + 浏览器 Notification API | 页面打开时可靠工作，权限授权后可发系统通知 | 页面关闭即失效 |
| B. Service Worker + 定时检查 | 同源页面在后台时仍可触发 | 浏览器调度不保证准时，Safari 限制多 |
| C. 桌面端封装（Tauri / Electron） | 真正的系统级定时提醒 | 交付形态变重，偏离「网页项目」 |

**结论**：待定（倾向 A，并把浏览器限制在 README 中明确说明——面试时主动说明限制比藏起来更好）

## D4. 数据持久化

候选：`localStorage`（简单，~5MB 上限）/ `IndexedDB`（容量大，适合课程与对话记录）/ 后端数据库。

**结论**：待定（倾向 IndexedDB）

## D5. 学习计划的生成方式

候选：纯规则排期（按 DDL、科目权重、可用时间段自动排）/ AI 生成后人工编辑 / 两者结合（规则兜底 + AI 润色）。

**结论**：待定

## D6. MVP 范围

面试作品的关键是**有一个能跑通的完整闭环**，而不是功能列表很长但每个都半成品。

初步设想：**课程导入 → AI 生成学习计划 → 今日待办 → 到点提醒**，四个环节串成一条可演示的主线。

**结论**：待定
